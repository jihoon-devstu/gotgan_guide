00결론 요약

질문마다 결론부터 적고, 이유와 예시는 해당 장에서 설명합니다.

질문추천 결론장
서비스를 어떤 기준으로 나누나액터(유저/판매자/관리자)가 아니라 업무 기능(데이터 소유권) 기준. 게이트웨이 + 업무 서비스 5개(user · store · product · order · settlement). "유저 도메인"은 서비스 1개면 충분합니다.03
업무 분장회의에서 재결정. 인프라 담당(A: AWS · B: CI/CD · C: 관측성)은 유지하고, 도메인은 4명의 숙련도를 고려해 다시 나눕니다. 이 문서는 서비스별 난이도와 숙련도별 배정 원칙, 참고안 2개를 제공합니다.03
EC2 크기EKS 워커 노드 t3.large × 2(최대 3, 디스크 40GiB gp3, OS는 AL2023). 우분투는 EKS 노드가 아니라 개발용 VM · 작업용 EC2에 쓰는 것을 추천.04
서빙 도메인프론트는 Vercel(기본 HTTPS · PR 미리보기), API는 NLB에 고정 IP(EIP)를 붙이고 DuckDNS 주소를 연결. Vercel rewrites로 /api/*를 API로 넘겨 브라우저에서는 같은 출처로 보이게.05
서비스별 DBMySQL 물리 1대 + 서비스별 스키마·계정 분리. 다른 서비스 테이블에 대한 FK·JOIN 금지, ID만 참조하고 필요한 값은 스냅샷으로 복사. 스키마 변경은 서비스마다 Flyway로.06
Saga 오케스트레이션주문 생성(재고 예약 → 포트원 결제 검증)과 결제 후 주문 취소 두 곳만. order-service가 오케스트레이터, 동기 REST 호출 + 보상 트랜잭션 + saga 상태 테이블.06
결제포트원(PortOne) V2 테스트 채널. 브라우저 SDK로 결제창 → 서버가 포트원 API로 금액·상태 검증 → 실패·위변조 시 자동 취소. 사업자 없이 테스트 상점으로 구축.07
인증 · 인가Spring Cloud Gateway + Spring Security + JWT. Keycloak은 자원·학습 비용 대비 이득이 작음.08
Redis · DynamoDBRedis: 장바구니, 리프레시 토큰, (선택) 상품 캐시. DynamoDB: Lambda가 쓰는 데이터(알림 이력·멱등 처리·이미지 작업 상태)와 키로만 찾는 데이터.09
EDA · 스케줄러EDA: 서비스 간 "일어난 일 통보"(입점 승인, 결제 완료, 구매확정, 정산 지급) → SNS + SQS. 스케줄러: 자동 구매확정, 주간 정산 집계, 결제 대기 만료, 보완요청 자동 반려, saga 복구.10
서버리스유저: 주문·배송 알림 메일 / 판매자: 상품 이미지 썸네일 생성 / 관리자: 정산 명세서 생성·발송. 모두 이벤트 트리거 Lambda.11
Jenkins vs GitHub ActionsGitHub Actions + ArgoCD. 서버 관리가 없고, OIDC로 AWS 키 없이 배포, 모노레포 경로 필터·서버리스 배포까지 한 곳에서. 프론트는 Vercel Git 연동.12
로깅학습 가이드의 PLG + Zipkin 구성을 그대로 시작하고, 로그 형식·라벨 규칙 통일 + 비즈니스 지표 + Lambda용 CloudWatch 데이터소스를 더함.13
백엔드 구조모노레포 하나에 services/(서비스별 독립 Gradle 프로젝트 · Dockerfile) · infra/terraform/ · deploy/(k8s · Helm · ArgoCD) · serverless/ · frontend/. 서비스 내부는 도메인별 패키지 + api/application/domain/infra 계층.15

이 문서가 둔 가정 (회의에서 확인)

이 문서의 전제
  1. 팀은 4명입니다. 원래 3명일 때 A(본인) = 스토어 관리자 + AWS 인프라, B = 유저 + CI/CD, C = 판매자 + 관측성 인프라로 나눴고, 1명(D)이 새로 합류했습니다. 인프라 담당은 유지하고, 도메인 배정은 회의에서 다시 정합니다(03장에 판단 자료).
  2. 숙련도: A는 부트캠프 수준 웹 프로젝트 4~5회(AWS·MSA는 처음), B는 전공자 · 웹 개발 2~3번째, C는 웹 개발·팀 프로젝트 모두 처음(Git부터 시작), D는 비전공자 · 웹 프로젝트 2~3번째.
  3. 결제는 포트원(PortOne) 테스트 채널로 실제 결제 흐름을 연동합니다. 사업자가 아니므로 테스트 상점 · 테스트 키만 씁니다(07장).
  4. 택배사 연동은 하지 않습니다. 판매자가 송장번호를 직접 입력하고, 배송완료는 판매자 버튼 또는 스케줄러로 흉내 냅니다.
  5. AWS 계정 하나를 팀이 공유하고, 환경은 dev 하나입니다. 유료 도메인 없이 Vercel(프론트) + DuckDNS(API)로 서빙합니다(05장).
  6. "협업 툴은 GitHub Action"은 GitHub(Issues · Projects · PR) + Actions로 해석했습니다.
  7. "EC2는 우분투"는 EKS 워커 노드 OS를 우분투로 하겠다는 뜻일 수도 있습니다. 04장에서 왜 노드는 AL2023을 추천하는지 설명합니다.

6주에 MSA를 처음 하는 팀이 지켜야 할 원칙

  1. 걷는 뼈대(Walking Skeleton) 먼저. 1주차 안에 "빈 서비스 6개가 NLB → 게이트웨이 → 각 서비스로 응답하고, Grafana에 보이고, push하면 자동 배포"까지 끝냅니다. 기능은 그 위에 얹습니다.
  2. 서비스 수는 적게. 한 사람이 2개 넘는 서비스를 맡지 않게 합니다. 쪼개기보다 합치기가 쉽습니다.
  3. 계약(API · 이벤트) 먼저, 구현은 나중. OpenAPI 명세와 이벤트 스키마를 먼저 합의하면 프론트는 MSW로, 백엔드는 각자 병렬로 개발할 수 있습니다.
  4. 통합은 매주. 매주 금요일 dev 클러스터에서 E2E 시나리오를 한 번씩 돌려 봅니다. 6주차에 처음 합치면 반드시 실패합니다.
  5. MVP 범위를 잘라 둔다. 목업 화면 43개를 전부 만들 수 없습니다. 16장의 범위표로 Must만 먼저 끝냅니다.

02목표 아키텍처

학습 가이드의 구조(VPC · EKS · LBC → NLB → Spring Cloud Gateway, CoreDNS, PLG, GitHub Actions + ArgoCD)를 유지하고, 업무 서비스와 AWS 관리형 자원(S3 · SNS/SQS · Lambda · SES · DynamoDB · Secrets Manager), 외부 서비스(Vercel · DuckDNS · 포트원)를 더한 모습입니다.

단계요청 하나가 지나가는 길 (예: 주문하기)
1브라우저 → Vercel(https://gotgan.vercel.app/api/orders) → rewrite → DuckDNS(gotgan-api.duckdns.org = NLB 고정 IP) → 게이트웨이 파드
2게이트웨이가 JWT 서명·만료·역할을 확인하고 X-User-Id, X-User-Roles 헤더를 붙여 order-service로 전달

4커밋 뒤 OrderPaid 이벤트를 SNS에 발행 → SQS → 알림 Lambda가 SES로 주문 확인 메일 발송
5모든 단계가 같은 traceId로 Loki(로그) · Zipkin(트레이스)에 남고, Prometheus가 지표를 수집

03서비스 분할 기준 · 업무 분장

질문: 각 도메인을 MSA로 나눌 때 어떤 기준으로 서비스와 서버를 나누는가? 유저 도메인은 서비스 하나인가 여러 개인가?

먼저 용어 정리: "서비스"와 "서버"

말이 프로젝트에서의 뜻나누는 기준
서비스 (마이크로서비스)독립적으로 빌드·배포되는 단위. 저장소 폴더 1개 = Spring Boot 앱 1개 = 이미지 1개 = Deployment 1개업무 기능과 데이터 소유권
서버 (노드)파드가 올라가는 EC2. 모든 서비스가 노드 2~3대를 함께 씁니다자원량(메모리·파드 수). 서비스마다 서버를 따로 두지 않습니다
파드 레플리카같은 서비스의 복제본. 부하·가용성 때문에 늘립니다트래픽. dev에서는 게이트웨이 2, 나머지 1~2

서비스를 나누는 6가지 질문

  1. 이 데이터의 주인은 누구인가? 한 테이블을 "쓰는(INSERT/UPDATE)" 서비스는 하나여야 합니다. 두 서비스가 같은 테이블을 고치면 그건 하나의 서비스입니다.
  2. 반드시 한 트랜잭션으로 묶여야 하는가? 주문(orders)과 상품주문(order_item)은 항상 함께 바뀌므로 같은 서비스. 주문과 재고는 잠시 어긋나도 보상할 수 있으므로 다른 서비스여도 됩니다(Saga).
  3. 변경 이유가 같은가? 정산 규칙이 바뀔 때 함께 고쳐야 하는 코드는 한곳에 둡니다.
  4. 부하 특성이 다른가? 상품 조회는 많고 정산 배치는 주 1회. 다르면 나눌 이유가 됩니다.
  5. 한 사람(또는 한 팀)이 책임질 수 있는가? (Conway의 법칙) 4명이면 서비스 4~6개가 상한입니다.
  6. 나누면 호출이 얼마나 생기는가? 화면 하나를 그리려고 서비스 3~4개를 매번 동기 호출해야 한다면 경계가 잘못된 것입니다.

왜 "유저/판매자/관리자" 기준 분할이 위험한가

액터 기준으로 나누면 같은 데이터를 여러 서비스가 고치게 됩니다. 주문 하나를 예로 들면:

행위액터액터 기준이면기능 기준이면
주문 생성유저user-service가 주문 테이블에 INSERT모두 order-service가 자기 테이블을 변경. 화면만 액터별로 다름
발주확인 · 송장 등록판매자seller-service가 같은 주문 테이블을 UPDATE
구매확정유저user-service가 다시 UPDATE
정산 조회관리자admin-service가 주문 테이블을 JOIN
결과: 분산 모놀리스 DB를 공유하거나, 서로의 API를 촘촘히 호출해야 해서 "배포는 따로인데 장애와 변경은 같이 오는" 최악의 구조가 됩니다. 상품도 같습니다. 판매자가 등록하고, 유저가 조회하고, 관리자가 판매중지합니다. 데이터의 주인은 하나(product-service)여야 합니다.

액터 구분은 API 경로(/api/seller/**, /api/admin/**)와 권한, 그리고 프론트 화면 영역으로 표현하면 됩니다.

왜 Vercel이 API까지 대신 받아 넘기나 (rewrite)

HTTPS 페이지(https://gotgan.vercel.app)에서 HTTP API(http://gotgan-api.duckdns.org)를 직접 부르면 브라우저가 혼합 콘텐츠(Mixed Content)로 막습니다. 그래서 브라우저는 https://gotgan.vercel.app/api/...만 부르고, Vercel 서버가 이를 DuckDNS 주소로 넘기게(rewrite) 합니다.

  • 브라우저 입장에서 프론트와 API가 같은 출처 → CORS 설정이 거의 필요 없음
  • 리프레시 토큰 쿠키가 퍼스트파티로 동작(08장)
  • 포트원 웹훅 주소도 https://gotgan.vercel.app/api/payments/webhook으로 HTTPS 주소를 줄 수 있음(07장)

1단계 · NLB에 고정 IP 붙이기 (A)

DuckDNS는 IP 주소(A 레코드)만 등록할 수 있습니다. LBC가 만든 NLB는 DNS 이름만 있고, 다시 만들면(helm uninstall · ArgoCD 재생성) IP가 바뀝니다. Terraform으로 EIP를 미리 만들어 NLB에 지정하면 NLB를 다시 만들어도 IP가 유지됩니다.

resource "aws_eip" "nlb" {
  count  = 2
  domain = "vpc"
  tags   = { Name = "sesac-team1-nlb-eip-${count.index}" }
}

이 구성의 한계와 1주차 검증 항목
  • Vercel → DuckDNS 구간은 암호화되지 않은 HTTP입니다. 브라우저 ↔ Vercel은 HTTPS지만 Vercel ↔ AWS 구간에서 토큰·비밀번호가 평문으로 지나갑니다. dev 시연용으로만 쓰고, 테스트 계정에 실제 비밀번호를 쓰지 않습니다.
  • Vercel의 외부 rewrite가 HTTP 대상과 응답 시간에서 문제없이 동작하는지 1주차 걷는 뼈대 단계에서 바로 확인하세요. 막히면 NLB 앞에 CloudFront를 두어 HTTPS 주소(https://xxxx.cloudfront.net)를 만들고 그 주소로 rewrite하는 방법이 대안입니다.
  • Vercel 무료(Hobby) 플랜은 개인·비상업 용도이고, GitHub 조직(Organization)의 비공개 저장소 연결에 제약이 있을 수 있습니다. 저장소를 공개로 두거나 한 사람 계정에 연결하는 방식을 미리 확인하세요.
  • 게이트웨이가 보는 클라이언트 IP는 Vercel 서버 IP입니다. 실제 IP는 X-Forwarded-For 헤더로 읽습니다.
  • 삭제 순서: EIP는 NLB가 잡고 있으므로 gateway Service(NLB)를 먼저 지운 뒤 app/을 destroy 합니다.
여유가 있다면 · 실무에서는 API에도 HTTPS를 붙이려면 클러스터에 cert-manager + Let's Encrypt(DuckDNS는 TXT 레코드를 지원하므로 DNS-01 방식 웹훅 사용)로 인증서를 받아 게이트웨이에서 TLS를 종료할 수 있습니다. ACM 인증서는 CNAME 검증이 필요해 DuckDNS 도메인에는 쓰기 어렵습니다. 실무에서는 Route53 도메인 + ACM 인증서 + ALB/CloudFront(+WAF)가 표준입니다(20장).

#!/bin/bash
# .sql 파일은 환경 변수를 치환하지 못하므로 .sh로 작성한다.
# *_DB_PASSWORD 는 Secret(← Secrets Manager)에서 mysql 컨테이너 환경 변수로 주입
# MySQL 시간대는 StatefulSet args --default-time-zone=+09:00 으로 고정 (JDBC · JVM도 Asia/Seoul)
set -e
for svc in user store product order settlement; do
  pw_var="$(echo "$svc" | tr a-z A-Z)_DB_PASSWORD"
  mysql -uroot -p"$MYSQL_ROOT_PASSWORD" <<SQL
CREATE DATABASE IF NOT EXISTS ${svc}db CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER IF NOT EXISTS '${svc}'@'%' IDENTIFIED BY '${!pw_var}';
GRANT ALL PRIVILEGES ON ${svc}db.* TO '${svc}'@'%';   -- 자기 스키마 밖은 볼 수 없다
SQL
done

Flyway — 이 구조에서도 쓰는 것이 좋은가? → 예, 처음부터 넣으세요

Flyway는 V1__init.sql, V2__...sql처럼 번호 붙은 SQL 파일을 순서대로 한 번씩만 실행하고, 어디까지 실행했는지를 DB의 flyway_schema_history 테이블에 기록하는 스키마 버전 관리 도구입니다. 앱이 뜰 때 아직 실행하지 않은 파일만 실행합니다.

이 프로젝트의 상황Flyway가 없으면Flyway가 있으면
스키마 5개, 각 주인은 서비스 (Database per Service)누가 언제 어떤 ALTER를 했는지 아무도 모름스키마 변경이 서비스 코드와 같은 PR에 들어가 리뷰됨. 서비스 폴더만 보면 그 DB의 역사가 다 있음
같은 스키마가 4곳 이상: 각자 로컬 docker compose, CI의 Testcontainers, dev 클러스터 MySQL"내 로컬에선 되는데" — 환경마다 테이블 모양이 다름어디서 띄우든 같은 파일로 같은 스키마가 만들어짐
ArgoCD 자동 배포배포 전에 누군가 kubectl exec mysql로 손으로 ALTER → 순서 꼬이면 장애새 이미지가 뜰 때 앱이 스스로 마이그레이션 → 코드와 스키마가 함께 이동
비용 때문에 클러스터를 지웠다 다시 만듦테이블·시드 데이터를 다시 손으로빈 MySQL에서 마이그레이션 + 시드가 자동 실행 → 바로 시연 가능
JPA ddl-auto=update 유혹컬럼 삭제·이름 변경이 반영되지 않고, 인덱스·제약을 통제할 수 없음. 운영에선 금지ddl-auto=validate로 두면 엔티티와 테이블이 다를 때 기동 시점에 바로 실패해 알려 줌

Flyway 규칙 4가지
  1. 이미 적용된 파일은 절대 고치지 않습니다. 고치면 체크섬이 달라져 Validate failed: Migration checksum mismatch로 앱이 뜨지 않습니다. 바꾸고 싶으면 새 번호 파일을 추가합니다. (로컬에서만 실수했다면 로컬 DB를 지우고 다시 시작)
  2. 되돌리기도 새 파일로 합니다(무료판에는 undo가 없음).
  3. 같은 서비스를 두 명이 작업하면 PR 머지 전에 번호가 겹치지 않는지 확인합니다.
  4. 컬럼 삭제·이름 변경처럼 위험한 변경은 "새 컬럼 추가 → 코드 전환 → 옛 컬럼 삭제"의 두 번 배포로 나눕니다(expand/contract). 롤링 업데이트 중에는 옛 버전 파드와 새 버전 파드가 같은 DB를 함께 쓰기 때문입니다.

@Component
@RequiredArgsConstructor
public class PlaceOrderSaga {

    private final OrderTxService orderTx;           // 로컬 트랜잭션 메서드 모음 (@Transactional)
    private final SagaStore sagaStore;              // saga_instance 기록 (각 호출이 짧은 트랜잭션)
    private final ProductStockClient stockClient;   // product-service /internal 호출
    private final PortOneClient portOne;            // 포트원 결제 조회·취소 API (07장)

    // ⚠ 이 클래스의 메서드에는 @Transactional 을 붙이지 않는다.
    //    원격 호출을 DB 트랜잭션 안에 넣으면 커넥션을 오래 잡고, 롤백해도 원격 쪽은 되돌아가지 않는다.

    // [요청 1] POST /api/orders — 주문서 제출
    public PrepareResult prepare(PlaceOrderCommand cmd) {
        Order order = orderTx.createPending(cmd);                     // T1: 주문 PENDING + payment READY
        SagaInstance saga = sagaStore.start(SagaType.PLACE_ORDER, order.getId());
        try {
            stockClient.reserve(new ReserveStockRequest(saga.getSagaId(), order.stockLines()));   // T2 (product)
            sagaStore.advance(saga, SagaStep.STOCK_RESERVED);             // 이제 결제 대기 (최대 15분)
            return PrepareResult.of(order.getOrderNo(), order.getPaymentId(), order.getPayAmt(), order.orderName());
        } catch (Exception e) {
            compensate(saga, order.getId(), e);                            // 재고 부족 등 → 결제창을 띄우지 않음
            throw new OrderFailedException(toUserMessage(e));
        }
    }

    // [요청 2] POST /api/orders/{orderNo}/payment — 결제창이 끝난 뒤 브라우저가 호출
    public CompleteResult complete(String orderNo, String paymentId) {
        Order order = orderTx.getPending(orderNo);
        SagaInstance saga = sagaStore.findByOrderId(order.getId());
        try {
            // 브라우저가 "결제 성공"이라고 해도 믿지 않는다 → 포트원에 직접 물어본다
            PortOnePayment p = portOne.getPayment(paymentId);              // T3
            if (!p.isPaid() || p.amount() != order.getPayAmt()) {
                throw new PaymentMismatchException(paymentId);             // 미결제 또는 금액 위·변조
            }
            sagaStore.advance(saga, SagaStep.PAYMENT_VERIFIED);
            orderTx.markPaid(order.getId(), p);                            // T4: PAID + OrderPaid 이벤트 기록
            sagaStore.complete(saga);
            return CompleteResult.success(orderNo);
        } catch (Exception e) {
            compensate(saga, order.getId(), e);
            return CompleteResult.failed(orderNo, toUserMessage(e));
        }
    }

    // 보상은 "역순"으로, 그리고 모두 멱등하게.
    // 타임아웃처럼 '성공했는지 모르는' 호출이 있을 수 있으므로, 시도했을 가능성이 있는 단계는 전부 되돌린다.
    void compensate(SagaInstance saga, Long orderId, Exception cause) {
        sagaStore.compensating(saga, cause.getMessage());
        try {
            portOne.cancelIfPaid(orderTx.paymentIdOf(orderId), "주문 처리 실패");   // 결제 안 됐으면 아무 일도 안 함
            stockClient.release(saga.getSagaId());        // 예약 없으면 아무 일도 안 함
            orderTx.markFailed(orderId, cause.getMessage());
            sagaStore.compensated(saga);
        } catch (Exception again) {
            // 보상도 실패 → FAILED 로 남기고 복구 배치(SagaRecoveryJob)가 다시 시도
            sagaStore.fail(saga, again.getMessage());
        }
    }
}

@Service
@RequiredArgsConstructor
public class StockReservationService {

    private final ProductOptionRepository optionRepo;
    private final StockReservationRepository reservationRepo;

    @Transactional
    public void reserve(String sagaId, List<StockLine> lines) {
        if (reservationRepo.existsBySagaId(sagaId)) {
            return;                                            // 같은 요청 재시도 → 이미 처리됨 (멱등)
        }
        for (StockLine line : lines) {
            // UPDATE product_option SET stock = stock - :qty WHERE product_option_id = :optionId AND stock >= :qty
            int updated = optionRepo.decreaseStock(line.optionId(), line.quantity());
            if (updated == 0) {
                throw new OutOfStockException(line.optionId()); // 트랜잭션 롤백 → 앞서 줄인 재고도 원복
            }
        }
        reservationRepo.save(StockReservation.of(sagaId, lines));
    }

    @Transactional
    public void release(String sagaId) {
        reservationRepo.findBySagaIdAndReleasedFalse(sagaId).ifPresent(r -> {
            r.lines().forEach(l -> optionRepo.increaseStock(l.optionId(), l.quantity()));
            r.markReleased();                                  // 두 번 호출돼도 한 번만 복원
        });
    }
}

    private final PlaceOrderSaga placeOrderSaga;

    @Scheduled(fixedDelay = 60_000)
    @SchedulerLock(name = "saga-recovery", lockAtMostFor = "50s")   // 레플리카 2개여도 한 파드만 실행 (ShedLock)
    void recover() {
        // ① 결제 대기 15분 초과: 결제창을 닫았거나, 결제 후 브라우저가 꺼져 [요청 2]가 오지 않은 경우
        //    → 포트원에 결제 여부를 물어 PAID면 앞으로 진행(complete), 아니면 되돌림(compensate)
        sagaStore.findWaitingPayment(Duration.ofMinutes(15))
                 .forEach(placeOrderSaga::resolveByPortOne);

        // ② 파드가 saga 도중 죽어 STARTED/COMPENSATING 으로 남은 경우 → 보상 재시도
        sagaStore.findStuck(Duration.ofMinutes(5))
                 .forEach(saga -> placeOrderSaga.compensate(saga, saga.getOrderId(),
                                                           new IllegalStateException("timeout recovery")));
    }
}

  • 실서비스(실결제) 전환은 사업자 등록과 PG 계약이 필요하므로 범위 밖(Won't)입니다.

                    .pathMatchers(HttpMethod.POST, "/api/payments/webhook").permitAll() // 포트원 웹훅 (서명은 order가 검증)
                    .pathMatchers("/actuator/health/**", "/actuator/prometheus").permitAll()
                    .pathMatchers(HttpMethod.GET, "/api/products/**", "/api/stores/**", "/api/categories/**").permitAll()
                    .pathMatchers("/api/seller/**").hasRole("SELLER")
                    .pathMatchers("/api/admin/**").hasRole("ADMIN")
                    .anyExchange().authenticated())
            .oauth2ResourceServer(o -> o.jwt(jwt -> jwt.jwtAuthenticationConverter(rolesConverter())))
            .build();
}

학습 가이드의 UserHeaderConfig(클라이언트가 보낸 X-User-Id 제거 후 토큰의 sub로 다시 붙이기)에 X-User-Roles, X-Store-Id도 같은 방식으로 추가합니다. 각 서비스는 이 헤더를 읽는 작은 @CurrentUser AuthUser 인자 리졸버를 공통 템플릿으로 갖습니다.

자주 하는 실수
  • Spring Security 7(Boot 4)에서는 .and() 체이닝이 없고 람다 DSL만 됩니다. Boot 2 시절 블로그 코드를 복사하면 컴파일되지 않습니다.
  • 내부 서비스가 헤더를 믿는 전제는 "게이트웨이를 거치지 않으면 닿지 않는다"입니다. 업무 서비스의 Service 타입은 반드시 ClusterIP로 두세요.
  • 게이트웨이는 WebFlux입니다. @EnableWebSecurity/HttpSecurity(MVC용)가 아니라 @EnableWebFluxSecurity/ServerHttpSecurity를 씁니다.

발행: 커밋된 뒤에만

1단계(기본) — @TransactionalEventListener(phase = AFTER_COMMIT)에서 SNS로 발행. 롤백된 주문의 이벤트가 나가지 않습니다. 단, 커밋 직후 파드가 죽으면 이벤트가 유실될 수 있습니다.

2단계(여유 시) — Transactional Outbox: 같은 트랜잭션에서 outbox_event에 INSERT → 스케줄러가 2초마다 NEW를 읽어 SNS 발행 후 SENT. 유실이 없습니다.

소비: 멱등하게

SQS는 최소 한 번 전달이라 같은 메시지가 두 번 올 수 있습니다. 소비자는 processed_event(event_id PK)에 INSERT를 시도해 중복이면 건너뜁니다. 처리 중 예외가 나면 메시지를 삭제하지 않아 재시도되고, 3번 실패하면 DLQ로 갑니다.

Spring에서 SQS를 받을 때 Spring Cloud AWS의 Boot 4 호환 버전을 먼저 확인하고, 맞지 않으면 AWS SDK v2 SqsClient 롱폴링으로 직접 구현합니다.

import { SESv2Client, SendEmailCommand } from "@aws-sdk/client-sesv2";
import { DynamoDBClient } from "@aws-sdk/client-dynamodb";
import { DynamoDBDocumentClient, GetCommand, PutCommand } from "@aws-sdk/lib-dynamodb";

const ses = new SESv2Client({});
const ddb = DynamoDBDocumentClient.from(new DynamoDBClient({}));
const TEMPLATES = {
  OrderPaid:          (p) => [`[곳간] 주문이 완료되었습니다 (${p.orderNo})`, `${p.ordererName}님, 결제금액 ${p.payAmt.toLocaleString()}원`],
  OrderItemShipped:   (p) => [`[곳간] 상품이 출발했습니다`, `${p.productName} · ${p.courier} ${p.trackingNo}`],
  OrderItemCancelled: (p) => [`[곳간] 주문이 취소되었습니다`, `${p.productName} 취소 완료`],
};

export const handler = async (event) => {
  const failures = [];
  for (const record of event.Records) {
    try {
      const evt = JSON.parse(record.body);                  // Raw message delivery 켬 → 봉투 그대로
      const key = { pk: `USER#${evt.payload.buyerId}`, sk: `${evt.occurredAt}#${evt.eventId}` };
      const done = await ddb.send(new GetCommand({ TableName: process.env.TABLE, Key: key }));
      if (done.Item) continue;                               // 이미 보낸 이벤트 (멱등)

      const [subject, body] = TEMPLATES[evt.eventType](evt.payload);
      await ses.send(new SendEmailCommand({
        FromEmailAddress: process.env.FROM_EMAIL,
        Destination: { ToAddresses: [evt.payload.ordererEmail] },   // 주문 스냅샷 → user-service 호출 불필요
        Content: { Simple: { Subject: { Data: subject }, Body: { Text: { Data: body } } } },
      }));
      await ddb.send(new PutCommand({ TableName: process.env.TABLE, Item: {
        ...key, type: evt.eventType, subject, read: false,
        ttl: Math.floor(Date.now() / 1000) + 90 * 24 * 3600,
      }}));
    } catch (e) {
      console.error(JSON.stringify({ msg: "notify failed", messageId: record.messageId, error: e.message }));
      failures.push({ itemIdentifier: record.messageId });   // 이 메시지만 다시 큐로
    }
  }
  return { batchItemFailures: failures };
};
서버리스에서 꼭 막히는 곳
  • Serverless Framework v4는 로그인(라이선스 키)이 필요합니다. 소규모 조직은 무료지만 serverless login 또는 CI에 SERVERLESS_ACCESS_KEY를 넣어야 합니다. 팀 계정을 1주차에 만들어 두세요. 대안: AWS SAM, Terraform으로 Lambda 직접 배포.
  • SES는 처음에 샌드박스입니다. 검증된 이메일 주소로만 보낼 수 있으니 팀원 4명의 메일을 SES 자격 증명으로 검증해 두고, 테스트 회원 이메일도 그 주소들로 만드세요. 운영 전환 요청은 승인까지 시간이 걸립니다.
  • S3 트리거 무한 루프: 썸네일 Lambda가 같은 버킷의 같은 접두어에 저장하면 자기 자신을 다시 깨웁니다. 트리거는 originals/, 결과는 thumbs/로 분리.
  • sharp 바이너리: Lambda는 linux-x64이므로 WSL에서 npm install --os=linux --cpu=x64 sharp로 설치해 패키징.
  • Lambda를 VPC에 넣지 않습니다. VPC에 넣으면 S3·SES·DynamoDB 접근에 NAT나 VPC 엔드포인트가 필요해집니다. 클러스터 내부 API를 불러야 한다면 경계 설계를 다시 보세요(필요한 값을 이벤트에 담아 보내기).
  • Lambda 로그는 Loki가 아니라 CloudWatch Logs로 갑니다. Grafana에 CloudWatch 데이터소스를 추가해 한 화면에서 봅니다(13장).
"공개 API도 Lambda로" 하고 싶다면 API Gateway HTTP API의 JWT 오소라이저는 OIDC 발급자 주소와 JWKS(RS256 공개 키)를 요구합니다. user-service가 RS256으로 서명하고 /.well-known/openid-configuration, /.well-known/jwks.json을 공개하면 마이페이지 알림함 조회 같은 API를 Lambda로 만들 수 있습니다. HS256을 유지하면 Lambda 오소라이저를 직접 작성해야 합니다. 6주 범위에선 Could입니다.
